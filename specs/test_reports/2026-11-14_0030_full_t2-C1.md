## Verdict
PASS WITH ISSUES. The real-data chain runs end to end through its real entry
point. `run_pipeline.sh --config <stand-in>` submits the sequencer as PBS jobs
(D-098) under the fake PBS, and all eight stages S1-S8 run: none is pre-made.
S1-S2 use the repository's launcher stubs, changed so that they pass the
fixture's real artefacts on. S3-S6 use Sbi-extractor's real tools at
e9aeb55; S7-S8 use the real tuner and runner. The run was stopped twice at
stage boundaries (`--stop --wait`) and resumed. It ended `PIPELINE DONE`
with no job submitted twice, one driver at a time, the dependencies kept, and
every artefact with a matching sidecar. Each hand-over between producer and
consumer agrees with the files as written: S1's manifest reaches S4 through
S2's frozen copy; S4's plan is named by S5's record; S5's shards match S7's
identity, including the donors per part by sec. 2.3's rounding rule; every
trial and member argument checked comes from the configuration, except
`--num-bins` (F402); the finalist is the
ledger's lowest NLL; and L_bar, recomputed with scipy, matches to 1e-12. A
second run of the same configuration in another folder gives identical
banks, NLLs and L_bar. Purging search, best_fit and sim_bank, then running
`--retry` on the three, rebuilds them identically. The chain stops where it
must for a wrong S1 artefact, a plan altered under S5, a bad configuration
and a configuration change without the flag. Four MAJOR findings concern
cases off the committed path, each reproduced end to end:
- F401: an identity change (`split.fractions`) accepted while S7 runs is not
  refused, and the search mixes two report splits.
- F402: `search.flow.num_bins` never reaches the runner.

  holds theta = 1.0 exactly, which the runner refuses in the report split
  and trains on silently otherwise.
- F409: after the search is reset and run again, the run reports
  `PIPELINE DONE` with the previous search's best fit.

There are also two MINOR findings (F404, F405), three NOTEs (F406-F408) and
four problems in the spec. The regression suite gives the counts of t1-A.

## Problems in the spec
- S401: the unit of x in the extractor's banks. Sec. 2's Notation gives x in
  Hz (IFR), with the 2026-11-12 caveat "the extractor's banks not checked
  here". In run A's bank (the real Sbi-extractor tools, sidecar
  `scale_convention` per_electrode_mean, w_size 0.01 s, f_s 100 Hz), the
  smallest row mean of x is 0.0010. D-075's 0.1 Hz floor holds for
  mean(x) f_s, whose minimum is 0.1000 Hz. So x is per bin of w_size, not
  Hz, on the stand-in at least.
- S402: `search.arm` (sec. 3.1, "`arm` in the runner's arms") is validated,
  but no stage or tool reads it for a recorded data set (`config.py:103`
  only). The trials' arm comes from the campaign's configurations. What the
  key controls is not stated.
- S403: sec. 6 names no minimal configuration for S1-S8 of a recorded data
  set ("davinci" for the plain command; block 8 starts at S4 with S1-S3
  pre-made). This run had to build one from the tests' stand-in, with the
  stubs changed to pass real artefacts on.
- S404: the trial id covers the bank's contract digest, which covers the
  sha256 of S3's freeze and of the cohort manifest. The freeze holds
  `created_utc` and `sim_main`, and the stand-in's manifest holds absolute
  paths. So two builds of the same data give identical numbers under other
  trial ids (runs A and B), and after S3-S5 are re-run, an existing search
  folder is "of another identity". The spec does not say whether
  reproducibility under a fixed seed (sec. 4) extends to the trial ids.
- Already raised and not repeated: t1-D's S701 (sec. 3.1's tool list) and
  t1-A's S1/S3-S8 of 2026-10-20 (stale versions, round() ties, upper-case hex
  in a sidecar: `sha256_sidecar_ok` lowers the token,
  `stages/__init__.py:73`).
