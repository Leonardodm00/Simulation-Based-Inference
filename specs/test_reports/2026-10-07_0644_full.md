## Problems in the spec
- Every block entry is `Confirmed: inferred` (Blocks 1-6). The tests confirm that code and documents agree, but agreement between the code and a spec copied from it is not evidence of intent. The author should confirm each block.
- The exit-code contract is marked inferred (open question 2). F3 depends on it.
- SPEC sec. 3 says `[REPO]` inputs are never read from the working tree without the identity check. It does not say which paths each script must check, and in particular whether transitive imports count (hpc/joint/dsn_locate.py, hpc/dsn/). F1 assumes they do.
- Block 6: the canonical form does not say whether braces around a single-token script are normalised. `$x_{i}^{2}$` is reported as residual against a declared `$x^2_i$`.
- Block 4: "agree with numpy ... and with torch" gives no tolerance. The runner computes in float32 and FREEZE computes `burst_frac` in float32 even on float64 input. Measured float32-to-float64 agreement of the quoted column statistics is within 5e-4 relative.
- Block 5 names torch 2.10.x as the reference. It cannot run here (see above).
- E0 convention 12, as the spec restates it, says a `[RAN]` tag names the block of the governing script. Several `[RAN]` tags carry no block, or point to another document's script: E3 line 336 (`n_psi = 359708` `[RAN]` `[KB]` (P1)), and E4 "`[RAN]` (P5)", "(P7)", "(E3)". These are printed by out-of-coverage scripts or other blocks, and the spec does not say how such tags are verified.
- E3's "r2's constants" rows (Block 3 B4) use r2's margin, alpha, lambda_sep and miner. They do not use two other r2 config fields: `exclude_same_culture_positives: true` and `sep_gate_*`. P2 line 911 calls the gate retired and inert. Whether "r2's constants" should include them is not specified.
